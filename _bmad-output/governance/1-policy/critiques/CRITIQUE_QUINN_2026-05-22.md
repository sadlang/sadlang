## العقبة #8 — Schrödinger's Layers (تضارب مصادر الطبقات)

### التشخيص

- PMF v1.6 §2.2 يقول: "اقرأ M من LAYERS.json (حالياً 15)".
- مهارة `bmad-document-project` في المرحلة 1 تُولِّد `docs/parts/01..NN-*.md` بناءً على **مسحها الخاص** للجذر.
- لا توجد آلية تضمن أن المسحَين يُعطيان نفس النتيجة.

### السيناريو الكاثوليكي

- يضيف مساهم مجلداً `vm_jit/` كطبقة جديدة.
- `bmad-document-project` يكتشفه ويُضيف `docs/parts/16-vm-jit.md`.
- لكن LAYERS.json يبقى `M=15` (لم يُحدِّثه أحد).
- DoD المرحلة 1 يفشل: "روابط لكل الطبقات المُعرَّفة في LAYERS.json" — `vm_jit` غير معرَّف.
- النتيجة: تعطُّل DoD رغم أن العمل صحيح.

### السبب الجذري

غياب مصدر حتمي وحيد. الاعتماد على ذاكرة الوكيل لتحديث LAYERS.json يدوياً.

### الحل الجذري (TRIZ — Inversion Principle)

بدل أن يقرأ الوكيل LAYERS.json ويُقارن، **اجعل النظام يُحدِّث LAYERS.json آلياً**:

- إنشاء `scripts/scan_layers.py` يمسح الجذر ويُولِّد LAYERS.json.
- `monthly-pmf-check.yml` يستدعي `scan_layers.py --check` ويرفض البناء إذا اكتُشف انحراف.
- النتيجة: يستحيل تقنياً أن يتقادم LAYERS.json. القاعدة "اقرأ LAYERS.json" تختفي من ذاكرة الوكيل لأنها مضمونة.

## العقبة #9 — Agent-Signature بدون Root of Trust

### التشخيص

PMF v1.6 §5.2.2 اقترح:
```
Agent-Signature: <agent_name>:<sha256(session_id + story_id)>
```

### العيوب

1. `agent_name` يكتبه الوكيل نفسه — قابل للتزوير.
2. `session_id` متقلِّب (يأتي من VS Code) — لا يُمكن التحقق منه لاحقاً.
3. لا يوجد cryptographic root of trust.
4. SHA256 hash بدون توقيع رقمي = ختم بلاستيكي.

### السبب الجذري

إعادة اختراع نظام توقيع رقمي بدل استخدام البنية التحتية المتوفرة (Git/GitHub GPG).

### الحل الجذري (Constraints over Conventions)

- GPG signing إلزامي على `main` عبر Branch Protection.
- GitHub يرفض push لكوميت غير موقَّع تلقائياً.
- التحقق من استقلالية المراجِع يصبح ممكناً عبر `git log --show-signature` + GitHub API.
- النتيجة: لا حاجة لـ Agent-Signature في PR description. Git نفسه يحمل الهوية الموقَّعة.

**التوثيق:** `.github/BRANCH_PROTECTION_POLICY.md`.

## العقبة #10 — الأرقام السحرية المدفونة (12 طبقة بأشكال أخرى)

### التشخيص

PMF v1.6 يحوي 12+ رقماً سحرياً مدفوناً في النص:

| الرقم | الموقع | المخاطرة |
|---|---|---|
| 3 أسابيع | §2.2 سبرنت | تغيير السياسة → بحث وتعديل يدوي |
| 35 يوم | §8.1 max review gap | نفس المشكلة |
| 70% | §2.2 DoD نسبة عربية | نفس المشكلة |
| 300 كلمة | §2.2 DoD min words | نفس المشكلة |
| 2500 رمز | §4 copilot budget | نفس المشكلة |
| 18K / 25K | §4.1.1 ميزانية | نفس المشكلة |
| 30 يوم | §5.2.1 round-robin | نفس المشكلة |
| 4 ساعات | lock TTL | نفس المشكلة |

### السبب الجذري

تكرار **نفس الخطأ النظمي** الذي حدث مع "12 طبقة" — هذه المرة بأشكال أخرى. v1.6 أصلح خطأ واحداً (LAYERS.json) لكنه ترك 12 خطأً مشابهاً.

### الحل الجذري (Single Source Externalization)

- إنشاء `THRESHOLDS.json` يجمع كل الأرقام مع `_meta` و`rationale_ar`.
- PMF يُحيل إلى THRESHOLDS.json بدل تكرار الأرقام.
- monthly workflow يفحص وجود THRESHOLDS.json وصحته.
- أي تعديل لرقم يصبح PR واحد في ملف واحد بدل بحث وتعديل متعدد.
