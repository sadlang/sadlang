**الحالة:** مُعتمَد  
**التاريخ:** 2026-01-01  
**المرتبط بـ:** ADR-006b (pipeline التوليد التلقائي), ADR-007 (المنصة الوثائقية)  
**الأثر على:** epics.md (Story 2.1+), ADR-006b-spec.md (§3.1 مخطط المعمارية)

## 1. السياق

### الوضع الحالي

| العنصر | التفاصيل |
|--------|----------|
| مستودع المشروع | `C:\s_lang\s-programming-language\` (C++17 + Python + tests) |
| موقع الوثائق | `C:\s_lang\website\` — **مستودع منفصل** |
| المنصة | VitePress v1.6.3 (مُعدَّة بالكامل: i18n + RTL + Shiki) |
| الحالة الحالية | محتوى يدوي — لا صلة آلية بالمشروع |

### المشكلة

ADR-006b يُخطِّط لـ pipeline يُولِّد `.md` pages من YAML sources داخل المشروع — لكن لا يوجد تعريف لـ:
- **أين تُكتب** الملفات الناتجة (path mapping بين المشروع والموقع)
- **كيف تصل** الملفات الناتجة إلى الموقع المنشور (CI coupling)
- **متى تُفعَّل** عملية النشر (trigger mechanism)

### الخيارات المدروسة

| الخيار | الوصف | المزايا | العيوب |
|--------|--------|---------|--------|
| **A** | نقل `website/` داخل المشروع | مستودع واحد، CI مشترك، path مباشر | خلط C++ + npm، node_modules ضخمة |
| **B** | Git Submodule | مستودعان منفصلان لكن مُترابطان | صعوبة الصيانة، تحديث submodule يدوي |
| **C** | CI Dispatch عبر `workflow_dispatch` | مستودعان مستقلان تماماً | تعقيد CI، authentication tokens |
| **D** | npm package مشترك (`@sad-lang/docs-data`) | فصل نظيف مع إصدارات | overhead نشر لكل تغيير في docs |

## 2. القرار

**الخيار المُعتمَد: A — نقل `website/` داخل المشروع الرئيسي**

```
s-programming-language/
├── website/              ← ينتقل هنا من C:\s_lang\website\
│   ├── docs/             ← محتوى VitePress (مصدر يدوي + مُولَّد)
│   ├── .vitepress/       ← إعدادات VitePress
│   └── package.json      ← VitePress + plugins
├── data/docs/            ← مصادر YAML (input للـ pipeline)
└── scripts/codegen/      ← gen_docs.py يُولِّد → website/docs/
```

---

## 3. السبب الجوهري

### لماذا A وليس B أو C؟

- **Pipeline path مباشر:** `gen_docs.py` يكتب مباشرة في `website/docs/` — لا dispatch، لا tokens، لا sync.
- **CI trigger طبيعي:** تغيير في `data/docs/*.yaml` → trigger في نفس الـ push → `npm run build` في نفس workflow.
- **الحجم مقبول:** `node_modules/` + `website/build/` تُضافان إلى `.gitignore` — لا أثر على git history.
- **المشروع يضم بالفعل SDL2 + LLVM:** إضافة Node.js devDependency ليست سابقة جديدة.

### لماذا ليس B (Submodule)؟
Git Submodules معروفة بصعوبة الصيانة للمساهمين الجدد وتُعقِّد branching strategy.

### لماذا ليس C (CI Dispatch)?
يُضيف تعقيداً كبيراً (tokens، خطوتان للـ PR review) لمشروع في مرحلة مبكرة.

## 4. التغييرات اللازمة

### 4.1 جدول التغييرات

| التغيير | الوصف | الوقت |
|---------|--------|-------|
| نقل `C:\s_lang\website\` → `s-programming-language/website/` | `git mv` أو نسخ + commit جديد | Story 2.0 |
| `.gitignore`: إضافة `website/node_modules/`, `website/.vitepress/dist/`, `website/.vitepress/cache/` | تجنب commit للمبنيات | Story 2.0 |
| CMakeLists.txt: إضافة custom target `docs` يُشغِّل `npm run build` في `website/` | بناء الوثائق كجزء من build | Story 2.0 |
| GitHub Actions workflow جديد: `docs-deploy.yml` — يُنشر على `gh-pages` عند push لـ `main` | نشر تلقائي | Story 2.0 |
| حذف `mkdocs.yml` من جذر المشروع → `archived/docs/mkdocs_legacy.yml` | تنظيف — راجع ADR-007 | Story 2.0 |
| `scripts/codegen/gen_docs.py` يكتب output في `website/docs/` | ربط pipeline بالموقع | Story 2.1 |

### 4.2 Path Mapping المعتمَد

```
YAML source                              → output في website/
─────────────────────────────────────────────────────────────
data/docs/builtins/math.yaml            → website/docs/docs/stdlib/math.md
data/docs/builtins/strings.yaml         → website/docs/docs/stdlib/string.md
data/docs/lessons/*.yaml                → website/docs/docs/lessons/*.md
data/docs/api_reference/*.yaml          → website/docs/docs/api/*.md
```

> **ملاحظة:** VitePress `srcDir: './docs'` + `website/docs/docs/` = URL `/docs/...` — متوافق مع sidebar.ts الحالي.
