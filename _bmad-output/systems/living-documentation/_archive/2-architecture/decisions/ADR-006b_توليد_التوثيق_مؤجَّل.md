## 1. المشكلة المُراد حلّها (مستقبلاً)

قبل UTM-6:
- توثيق الكلمات المفتاحية والدوال وطرق الأنواع مكتوب **يدوياً** ويتقادم مع كل تغيير.
- لا تزامن بين `data/language/` و`docs/` — أي تغيير canonical لا يصل للموقع آلياً.
- مئات ملفات Markdown منتشرة بدون خطة ترحيل.

**الهدف المستقبلي:** أي تغيير في YAML ينعكس فوراً في الموقع بدون تدخل يدوي.

---

## 2. لماذا تأجَّل؟ (سجل رسمي)

### من وينستون (المعماري)
> "أقسام 1–8 = compiler infrastructure. القسم 10 = content pipeline. لهما SLA وفريق ومخاطر مختلفة. فشل القسم 10 (مرجَّح) سيُلوِّث سمعة الجوهر ويجمِّد التبني."

**المشاكل التقنية المُحددة:**
1. **Jinja2 + Markdown ≠ IR حقيقي** — قوالب Jinja تُنتج نصاً مسطحاً فاقداً للبنية المعنوية. لاحقاً لن تستطيع توليد LSP MarkupContent أو REPL playground أو man pages أو PDF بدون إعادة كتابة كل قالب.
2. **صفر versioning** — لا `since` لا `deprecated_in` لا `stability`. أول كسر API بعد UTM-6.13 يُسقط كل الدروس صامتاً.
3. **خطة ترحيل مفقودة كلياً** — ADR يفترض أرضاً فارغة لكن المستودع يحوي مئات MD يدوية. تجميد بين UTM-6.9 و UTM-6.13 = drift أسوأ من الوضع الحالي.
4. **enforce_docs_coverage كارثي** — المطورون سيتجاوزون بـ `visibility: internal` كاذب أو stubs صفرية.

### من د. كوين (حلّال المشكلات)
> "الـ13 مرحلة لا يمكن إيقافها بأمان — تخلق hybrid غير صالح للتشغيل."

**نتائج اختبار المعايير الخمسة:** 0 ناجح / 2 جزئي / 3 فاشل.

**السؤال الصعب:**
> *"مَن في فريقك سيكتب الدرس رقم 47 عن الاستعارة المتعددة المستويات في goroutines بصيغة YAML؟"*

**الإجابة المُعتمَدة:** وكيل AI (Claude Sonnet 4.6 أو خلفه) يكتب الدرس بأسلوب بشري طبيعي — بمدخل YAML للمواصفات + CI يختبر الأمثلة + مراجعة بشرية للجودة.

### من بايج (المراسلة التقنية)
> "MkDocs-only = lock-in قاتل — تحتاج 4 قنوات حداً أدنى."

## 4. الأسئلة المفتوحة (تُجاب قبل المتابعة)

### السؤال أ: MkDocs أم Docusaurus؟

| المعيار | MkDocs Material | Docusaurus |
|---|---|---|
| Versioning | mike plugin (هش) | مدمج ✅ |
| i18n | إضافة منفصلة | مدمج ✅ |
| Playground | غير ممكن | ممكن مع React |
| Toolchain | Python خفيف | JS/Node ثقيل |
| Maturity | mature | mature ✅ |

**التوصية الأولية (وينستون):** Docusaurus — يحلّ versioning + i18n مجاناً.  
**الحاجة:** قرار نهائي بعد POC فعلي.

### السؤال ب: Diátaxis كـ schema؟
هل نُضيف حقل `type: tutorial|how-to|reference|explanation` إلى كل وثيقة؟  
ومَن يُطبِّق linter يرفض الخلط؟

### السؤال ج: enforce_docs_coverage — كيف نجنب الالتفاف؟
الخيارات:
1. إلزامي لكل API عام فقط (لا `visibility: internal`).
2. stubs مقبولة لكن مع flag `stub: true` يظهر في الموقع.
3. CI يرفض PRs بـ stub أكثر من 30 يوماً.

## 5. الرؤية المستقبلية (للمراجعة لاحقاً)

عندما يُرفع التجميد، هذا ADR يُوسَّع بـ:

### 5.1. Document-IR Schema المقترح
```json
{
  "doc_type": "reference|tutorial|how-to|explanation",
  "source_yaml": "data/language/type_methods.yaml",
  "source_item_id": "channel.send",
  "lang": "ar",
  "since": "0.1.0",
  "stability": "stable|experimental|deprecated",
  "sections": [
    { "type": "summary", "content": "..." },
    { "type": "parameters", "items": [...] },
    { "type": "example", "code": "...", "runnable": true }
  ]
}
```

### 5.2. قنوات المخرَج (4 حداً أدنى)
1. **MkDocs / Docusaurus** — الموقع الرئيسي.
2. **LSP MarkupContent** — يظهر في editors عند hover.
3. **REPL `:help`** — يظهر داخل REPL لغة ص.
4. **man pages** — `man sad-channel-send` في الطرفية.

### 5.3. مولِّد الدروس بالذكاء الاصطناعي
```
data/language/tutorials/
  lesson-047-multilevel-goroutine-borrow.yaml
    spec:
      type: tutorial
      topic: "الاستعارة المتعددة المستويات في goroutines"
      prereqs: [lesson-044, lesson-046]
      key_concepts: [goroutine, channel, borrow, lifetime]
    examples:
      - code: |  ← مُختبَر فعلاً بـ sad.exe
          أطلق
            متغير ق = قناة(5)
            ...
          نهاية
        expected_output: "..."
      
→ AI agent يقرأ هذا الـ spec ويكتب الدرس بأسلوب بشري
→ CI يختبر الأمثلة
→ مراجعة بشرية للجودة والأسلوب
```
