# جلسة الخبراء — الجولة الثانية: نقد ADR-006

**التاريخ:** 2026-05-15  
**النموذج:** Claude Sonnet 4.6   
**الجلسة:** جولة نقد ADR-006 من ثلاثة خبراء + قرار التقسيم  
**القرار المُتخذ:** الخيار 2 — تقسيم إلى ADR-006a و ADR-006b  

---

## ١. ملخص نقد الخبراء

### 📚 بايج — المراسلة التقنية

#### نقاط القوة (3)
1. توحيد SoT في YAML قرار صائب وفي وقته.
2. `enforce_docs_coverage` نادر وحاسم — يحوِّل التوثيق من "نية" إلى "عقد بنائي".
3. الفصل L1/L2/L3 نظيف ويحترم Single Responsibility.

#### نقاط الضعف (5)
| الترتيب | المشكلة | الوصف |
|---|---|---|
| 1 | Diátaxis مفقودة كـ schema | يجب إضافة حقل `type: tutorial\|how-to\|reference\|explanation` مع linter يرفض الخلط |
| 2 | MkDocs-only = lock-in قاتل | تحتاج 4 قنوات: MkDocs + LSP MarkupContent + REPL :help + man pages |
| 3 | Jinja2 lock-in | تحتاج IR وسيط (JSON) ثم renderers متعددة |
| 4 | صفر versioning | لا `since` لا `deprecated_in` لا `stability` |
| 5 | خطة هجرة مفقودة | `docs/` و`وثائق/` الموجودة = صفر خطة ترحيل |

#### الإضافات الإلزامية (3)
- Diátaxis-as-schema مع i18n عربي/إنجليزي.
- عقد LSP صريح (`lsp_hover.json` + `lsp_completion.json` في gen_all).
- مصفوفة هجرة (ملف → مصير → مالك → تاريخ) + فحص CI `docs_legacy_no_new_files`.

**الحكم:** ❌ لا — مع تعديل جوهري.

---

### 🏗️ وينستون — المعماري

#### نقاط القوة (3)
1. SoT صارم بـ `enforce_guards` يحوِّل القاعدة من اتفاق اجتماعي إلى failure في CMake.
2. `write_if_changed` + `GenerationContext` بدون global state → determinism ممتاز.
3. التقسيم Loader/Validator/Emit + orchestrator واحد يكسر التكرار.

#### نقاط الضعف (5 مرتَّبة من الأخطر)
| الترتيب | المشكلة | التأثير |
|---|---|---|
| أ | **خلط ADR واحد لمشكلتين منفصلتين** | أقسام 1–8 = compiler infra، قسم 10 = content pipeline — SLA ومخاطر مختلفة تماماً |
| ب | **Jinja2+Markdown ≠ IR حقيقي** | لاحقاً لن تستطيع توليد LSP/REPL/man/PDF بدون إعادة كتابة كل قالب |
| ج | **صفر versioning** | أول كسر API بعد UTM-6.13 يُسقط كل الدروس صامتاً — debt تراكمي لا يُصلح بأثر رجعي |
| د | **خطة ترحيل المحتوى مفقودة كلياً** | ADR يفترض أرضاً فارغة لكن المستودع يحوي مئات MD يدوية |
| هـ | **enforce_docs_coverage = نية ممتازة، تنفيذ كارثي** | المطورون سيتجاوزون بـ `visibility: internal` كاذب أو stubs صفرية |

#### تحليل Lock-in
| الأداة | التقييم |
|---|---|
| **Docusaurus** | الأقرب للاحتياج — versioning و i18n خارج الصندوق (✅ يحلّ ج و د مجاناً) |
| Astro/Starlight | component-based + playground — JS toolchain ثقيل |
| MkDocs Material | أبسط لكن versioning عبر mike plugin هش، صفر playground |

#### الطبقات المعمارية المفقودة (3)
1. LSP MarkupContent emitter.
2. Versioning + Stability axis (`since`, `deprecated_in`, `stability`).
3. Executable examples sandbox (`tools/doc_runner` بـ timeout وحد ذاكرة).

#### تقييم جدوى المراحل الـ13
- UTM-6.0 → 6.7: ✅ قابلة للتنفيذ بأمان.
- UTM-6.8 → 6.13: ❌ تخلق hybrid غير صالح للتشغيل:
  - 6.8: drift فوري في صفحة واحدة.
  - 6.10: نصف الموقع مولَّد ونصفه قديم = أسوأ تجربة قارئ.
  - 6.12: `enforce_docs_coverage` قبل اكتمال 6.13 = بلوكيج CI كامل.
  - **الأخطر:** لا rollback plan.

**الحكم:** ❌ لا — مع تعديل جوهري وتقسيم إلزامي.  
**توصية:** اعتمد UTM-6.0→6.7 كـ **ADR-006a**. أجِّل القسم 10 إلى **ADR-006b** بعد إدخال Document-IR حقيقي + خطة ترحيل ملموسة.

### 🔬 د. كوين — حلّال المشكلات

#### تحليل 5 Whys
**الجذر:** ADR-006 يخلط **reference docs** بـ **pedagogical docs** — خطأ إبستيمولوجي أساسي.

#### تناقض TRIZ
صرامة schema **vs** حرية تعبير المؤلف الإبداعية — ADR يحلّ نصف الصرامة فقط.

#### الافتراضات الخفية الكاذبة (3)
| الافتراض | لماذا خاطئ؟ |
|---|---|
| AI agents ستحترم الـguards | ستلتفّ عليها بنيوياً (gaming CI) |
| `example.runnable` مستقر للأبد | لا آلية snapshot-update |
| الـ13 مرحلة قابلة للإيقاف الآمن | تخلق hybrid غير صالح للتشغيل |

#### سجل المعايير الخمسة
| المعيار | النتيجة |
|---|---|
| Break test | ⚠️ جزئي |
| SoT-single test | ❌ فشل (Jinja2 تخلق dual SoT) |
| Marginal cost test | ❌ فشل (>>20%) |
| AI-friendly test | ⚠️ جزئي (تقنياً نعم، تربوياً لا) |
| Regression test | ❌ فشل (لا completeness check) |

**النتيجة: 0 ناجح / 2 جزئي / 3 فاشل.**

#### التوصية
- **ADR-006a:** توحيد الثوابت فقط (المراحل 6.0→6.4).
- **ADR-006b:** التوثيق التربوي — مؤجل حتى تعمل 006a لمدة 3 أشهر تحت حمل حقيقي.

#### السؤال الصعب
> *"مَن في فريقك سيكتب الدرس رقم 47 عن الاستعارة المتعددة المستويات في goroutines بصيغة YAML — وهل تثق أن المخرج سيكون أوضح من ملف Markdown يدوي؟ إن لم تستطع تسمية شخص واحد بالاسم الآن، فـ ADR-006b ميتة قبل أن تُولد."*

## ٤. إجابة سؤال د. كوين الصعب

**السؤال:** *مَن سيكتب الدرس رقم 47 عن الاستعارة المتعددة المستويات في goroutines بصيغة YAML؟*

**الإجابة الرسمية:**

> **وكيل ذكاء اصطناعي متخصص** سيكتب الدرس بأسلوب بشري طبيعي.

التفاصيل:
- **الكاتب:** وكيل AI (مثل Claude Sonnet 4.6 أو ما يخلفه) يعمل ضمن pipeline آلي.
- **الأسلوب:** يكتب الدرس بصيغة بشرية طبيعية باللغة العربية — ليس template machine-generated.
- **المدخل:** مواصفات YAML للمفهوم + أمثلة كود اختُبرت فعلاً + قيود Diátaxis (نوع: tutorial/how-to/reference).
- **المخرج:** Markdown جاهز للنشر يراجعه إنسان (مراجعة جودة، لا إنشاء من صفر).
- **الضمان:** كل درس يمر بـ CI يتحقق من:
  - أمثلة الكود تعمل فعلاً (تُشغَّل بـ sad.exe).
  - التوافق مع Diátaxis type المُعلَّن.
  - لا تناقض مع مرجع YAML (canonical names).

**لماذا هذا يُسكت المخاوف؟**
- يُجيب على "مَن" بالاسم: وكيل AI — كيان موجود ومُشغَّل الآن.
- يُجيب على "هل تثق؟": نعم، بشرط CI يتحقق من الأمثلة + مراجعة بشرية للجودة.
- لا يفترض قدرة إنسانية نادرة — يؤتمت الجزء الأصعب ويبقي للإنسان مهمة المراجعة.

**تحذير:** هذا لا يُسقط مطلب د. كوين بتأجيل ADR-006b — يظل التأجيل واجباً حتى تستقر ADR-006a.
