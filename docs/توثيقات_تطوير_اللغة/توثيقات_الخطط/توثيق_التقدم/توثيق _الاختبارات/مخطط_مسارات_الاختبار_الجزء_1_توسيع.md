> **الغرض:** توسيع الجزء الأول بمسارات إضافية حدية وشاملة تغطي كل الفجوات المحتملة بين المفسر والمترجم.  
> **الفلسفة:** لا تُترك حالة حدية دون اختبار — الصفر، الفارغ، لاشيء، القيم القصوى، التداخل العميق، التفاعل بين الميزات.  
> **الرمز:** 🔴 = حرج | 🟡 = مهم | 🟢 = تحسين | ⚠️ = فجوة محتملة بين المفسر والمترجم

### 🔴 الفجوات المكتشفة بين المفسر والمترجم — تحتاج إصلاحاً في `sadc`

1. **OE-006 / OE-029 — عامل الأسّ `**` يحوّل الأعداد الصحيحة إلى عشرية في المترجم** ✅ **أُصلحت**
   - المفسر: `2 ** 3 = 8` (نوع رقم)
   - المترجم (سابقاً): `2 ** 3 = 8.0` (نوع عشري)
   - **السبب الجذري:** في `sir_builder_operators.cpp` كان `OP_POWER` يُجبر `resultType = SadTypeKind::Float` دائماً، بينما `emitBuiltinPow` كان يحوّل النتيجة قسرياً إلى `i64` — فيُطبع integer bit pattern بتنسيق `%f`.
   - **الحل المطبَّق (BF-04 + BF-09):**
     - `compiler/src/frontend/sir_builder_operators.cpp`: حذف `resultType = SadTypeKind::Float;` من حالة `OP_POWER` للحفاظ على النوع المُستنتَج من المعاملين (نفس منطق `+`، `-`، `*`).
     - `compiler/src/backend/llvm/llvm_codegen_builtins_math_async.cpp`: في `emitBuiltinPow` — إجراء `CreateFPToSI` فقط إذا كان `inst->result->dataType != Float`؛ إذا كان Float نُبقي double.
   - **الاختبارات:** OE-006 و OE-029 الآن **تكافؤ مزدوج 100%**؛ لا تراجع في الـ 28 اختباراً الباقية.

2. **OE-039 — مقارنة `==` بين أنواع مختلفة تُخرج فارغاً في المترجم** ✅ **أُصلحت**
   - المفسر: `42 == "42"` ⇒ `خطأ` (مقارنة صارمة)
   - المترجم (سابقاً): ⇒ مخرج فارغ تماماً (LLVM IR مكسور)
   - **السبب الجذري:** في `sir_builder_operators.cpp`، عند وجود نص أحد الجانبين كان `isStringOp = true` بصرف النظر عن نوع الجانب الآخر، فيُولِّد `STRING_CMP` على `i64 + ptr` → `IR` غير صحيح.
   - **الحل المطبَّق (BF-04 + BF-09 + BF-10):** اختصار جذري قبل اختيار `SIROpcode` — إذا كانت العملية `==` أو `!=` وكان أحد المعاملين نصاً والآخر رقمياً/منطقياً (وليس parameter مُستنتَج)، تُرجع `BuildResult` بقيمة boolean ثابتة (`false` لـ `==`، `true` لـ `!=`) دون توليد أي تعليمة SIR.
   - **الاختبار:** OE-039 الآن **تكافؤ مزدوج 100%**؛ 30/30 اختبار يمر بدون تراجع.
   - **الموقع:** `compiler/src/frontend/sir_builder_operators.cpp` — كتلة `mixedTypes` قبل `switch (binOp->op)`.

3. **TE-001 — العامل الثلاثي يعامل `لاشيء` كـ truthy في المترجم** ✅ **أُصلحت**
   - المفسر: `لاشيء ? "أ" : "ب"` ⇒ `"ب"` (لاشيء falsy)
   - المترجم (سابقاً): ⇒ `"أ"` (لاشيء truthy)
   - **السبب الجذري:** `لاشيء` يُمثَّل بـ `kSadNullSentinel = -9223372036854775807`. في `emitCondBranch` (`llvm_codegen_branch_call.cpp`) كان التحويل i64→i1 عبر `cond != 0` فقط، فيعتبر sentinel الغير-صفرية truthy.
   - **الحل المطبَّق (BF-04 + BF-10):** في طبقة codegen الموحّدة (`emitCondBranch`)، للأعداد الصحيحة 64-بت نولّد الآن: `cond != 0 && cond != kSadNullSentinel`. هذا إصلاح جذري واحد يوحّد دلالة truthy/falsy في كل السياقات (إذا، بينما، الثلاثي، &&، ||).
   - **الاختبار:** TE-001 الآن **تكافؤ مزدوج 100%**؛ 30/30 اختبار يمر بدون تراجع.
   - **الموقع:** `compiler/src/backend/llvm/llvm_codegen_branch_call.cpp` (فرع i64 في تحويل الشرط إلى i1).

4. **VE-004 — كلمة `حالة` المُوصّفة كسياقية تتعامل كأنها محجوزة في `=`** ✅ **أُصلحت**
   - عند كتابة `حالة = 5` الـlexer/parser كان يُفسرها كبداية switch.
   - **السبب الجذري:** في `parser_main.cpp` (دالتي `parseDeclaration` و `parseStatement`)، lookahead السابق لـ `حالة` كان يستثني `(` و `.` فقط، فيتعامل مع `=` و`+=` و`[` كأنها تابعة لـ switch.
   - **الحل المطبَّق (BF-04 + BF-11):** توسيع استثناءات `حالة` بنفس النمط في الموضعين: إذا تلتها `=` أو `+=` أو `-=` أو `*=` أو `/=` أو `%=` أو `//=` أو `[` → تُعامل كمُعرّف عادي (الجملة تعبيرية/تعيين)، وإلا تُعتبر switch.
   - **الاختبار:** VE-004 وُسّع ليشمل `حالة` فعلياً، ويمر مزدوج 100%؛ switch العادي لا يزال يعمل؛ 30/30 اختبار بدون تراجع.
   - **الموقع:** `shared/parser/src/core/parser_main.cpp` (`parseDeclaration` + `parseStatement`).
