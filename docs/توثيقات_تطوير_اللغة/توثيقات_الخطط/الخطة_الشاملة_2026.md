## 1. الملخص التنفيذي

لغة ص مشروع طموح وفريد — **أول لغة برمجة عربية مكتملة** بمفسر ومترجم أصلي عبر LLVM. المشروع يحتوي على:
- **~106,000+ سطر كود C++** (frontend + backend + interpreter + builtins)
- **42 ملف SIR Builder** + **55 ملف LLVM Codegen** + **38 ملف مفسر (visitors + builtins)**
- **113 اختبار تنفيذ مزدوج** (جميعها dual مفسر+مترجم) — ✅ **المراحل 1 و2 و3 مكتملة**
- **25 اختبار شامل C++** (~700+ حالة اختبار في CI)
- **5 سير عمل CI/CD** (Windows + Linux + macOS)

### التحديات الرئيسية:
1. **~~فجوة اختبارات ضخمة~~** — ~~19 اختبار dual execution~~ → ✅ **68 اختبار** (المرحلة 1 مكتملة)
2. **ملفات متضخمة** — 13 ملف في SIR frontend فوق 800 سطر + 5 ملفات مفسر فوق 1900 سطر
3. **ميزات كثيرة بدون تغطية مزدوجة** — OOP, patterns, macros (التزامن أصبح مغطى ✅)
4. **عدم وجود Feature Matrix رسمية** — لا نعرف بدقة ماذا يدعم المترجم مقابل المفسر
5. **~~غياب اختبارات سلبية~~** — ✅ **5 اختبارات سلبية** (N01-N05) مكتملة ومتحققة
6. **~~تزامن بأعلى مخاطر~~** — ✅ **3 اختبارات تزامن** (057-059) تغطي goroutines + قنوات + select + مستقبل

### القرار الاستراتيجي:
**تجميد الميزات الجديدة** والتركيز على: اختبارات (إيجابية + سلبية) → إضافة dual إلى CI → تقسيم ملفات → توثيق → إطلاق MVP تعليمي مُضيّق.

### التغييرات عن النسخة 1.0:
- ⏰ **الجدول الزمني**: 16 → **24 أسبوع** (إجماع 4 وكلاء: التقديرات السابقة متفائلة 2x)
- 🧪 **اختبارات سلبية**: 5 اختبارات P0 لمسارات الخطأ (جديد — لم تكن في النسخة 1.0)
- ⚡ **التزامن**: نُقل من المرحلة 2 إلى المرحلة 1 (خطورة 25/25 لا يجب تأجيلها)
- 🎯 **MVP أضيق**: حذف لامدا/أنماط من MVP الطلابي (خلاف — Amelia تعارض)
- 📊 **مقاييس سلوكية**: معدل إكمال الدرس بدل نجوم GitHub
- 🏗️ **Strangler Fig**: منهجية التقسيم التدريجي بدل النقل الكامل
- 🎮 **Playground مبكر**: نُقل من المرحلة 5 إلى المرحلة 4
- 🔒 **بوابات أقوى**: code coverage ≥60% + negative tests + performance baselines

### 6.3 ADR-002: Interface Contract Specification (Winston)

> **الهدف:** تحديد الواجهات بين الطبقات قبل أي تقسيم. Strangler Fig بدون واجهات = فوضى.

**الأسئلة الثلاثة التي يجيب عليها ADR-002:**

1. **ما الواجهات؟** Lexer→Parser→AST→Interpreter, AST→SIR→LLVM
2. **ما النمط التقني؟** **Thin facade classes** (وليس abstract interfaces كاملة — أقل كلفة، نفس العزل)
3. **ما القاعدة؟** "لا يستورد أي مكون ملفات header من مكون غير مجاور في السلسلة"

**مثال:**
```cpp
// facades/IStatementExecutor.h — thin facade
class IStatementExecutor {
public:
    virtual ~IStatementExecutor() = default;
    virtual Value execute(const ASTNode& node) = 0;
    virtual void executeBlock(const std::vector<ASTNodePtr>& stmts) = 0;
};
```

> **ملاحظة:** Facades ليست refactoring شامل — هي wrappers رفيعة لعزل التبعية المباشرة.

### 6.4 🆕 Rollback Strategy (Winston v2.1)

## 9. المرحلة 3: إعادة الهيكلة — Strangler Fig Pattern (أسابيع 9-14)

### 9.1 الهدف

> **🆕 تغيير جوهري عن النسخة 1.0:** اعتُمدت منهجية **Strangler Fig** (Winston) بدلاً من النقل الكامل. نبدأ بالمفسر (الأصغر والأسهل) ثم SIR ثم LLVM.

### 9.2 منهجية Strangler Fig (إلزامية)

> **المبدأ:** بدلاً من نقل ملف كامل دفعة واحدة، نختار **دالة واحدة** وننقلها إلى ملف جديد مع wrapper في الملف الأصلي. ثم نختبر. ثم ننقل الدالة التالية. وهكذا.

```
الخطوة 1: حدد الدالة المراد نقلها (اختر الأقل ارتباطاً أولاً)
الخطوة 2: أنشئ الملف الجديد مع الدالة
الخطوة 3: في الملف الأصلي، أضف forward declaration أو #include
الخطوة 4: بناء + اختبار (65+ dual test)
الخطوة 5: إذا نجح → انتقل للدالة التالية
            إذا فشل → ارجع (git revert) وحلل السبب
```

**ترتيب التقسيم (تعديل Amelia + Winston):**
1. **المفسر أولاً** — أصغر حجماً، أسهل للاختبار، لا يعتمد على LLVM
2. **SIR Frontend ثانياً** — أكبر من المفسر لكن نمط الكود مشابه
3. **LLVM Backend أخيراً** — الأكثر تعقيداً، يحتاج فهم عميق للأنواع
