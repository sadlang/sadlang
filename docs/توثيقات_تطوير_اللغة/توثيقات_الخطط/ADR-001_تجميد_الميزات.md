# ADR-001: تجميد الميزات الجديدة — Architecture Decision Record

| الحقل | القيمة |
|-------|--------|
| **الرقم** | ADR-001 |
| **العنوان** | تجميد إضافة الميزات الجديدة حتى استقرار ما هو موجود |
| **الحالة** | ✅ مُعتمد |
| **التاريخ** | 2025-07-16 |
| **المؤلف** | فريق تطوير لغة ص |
| **المراجعون** | Winston (المعماري)، John (مدير المنتج)، Murat (مهندس الاختبار)، Amelia (المطورة) |
| **السياق** | الخطة الشاملة 2026 — المرحلة 0 |

## 1. السياق

لغة ص تمتلك حالياً **أكثر من 105,000 سطر كود C++** موزعة على 10 أنظمة رئيسية، وتدعم ميزات متقدمة تشمل:
- OOP كامل (أصناف، وراثة، سمات، امتدادات)
- مطابقة أنماط متقدمة
- تزامن (goroutines، قنوات، select)
- ماكروز، لامدا، إغلاقات
- مترجم LLVM كامل (SIR → LLVM IR → ملف تنفيذي)

**المشكلة**: رغم غنى الميزات، لا يوجد ضمان أن المفسر والمترجم يعطيان نتائج متطابقة. الاختبارات المزدوجة (dual execution) تغطي فقط **19 اختباراً** من أصل مئات المسارات الممكنة.

## 2. القرار

**نُجمّد إضافة أي ميزة لغوية جديدة** حتى تحقيق الشروط التالية:

1. **50+ اختبار dual execution** ناجح يغطي كل فئة ميزات (المرحلة 2)
2. **اختبارات سلبية** تثبت تطابق رسائل الخطأ بين المفسر والمترجم
3. **اختبارات تزامن** تثبت سلامة goroutines وقنوات في المترجم
4. **بوابة جودة MVP** (Gate 0) منجزة بنسبة 100%

## 3. المبررات

### 3.1 لماذا التجميد؟

| السبب | التوضيح |
|-------|---------|
| **الهشاشة** | كل ميزة جديدة تضاف بدون اختبار مزدوج تزيد الفجوة بين المفسر والمترجم |
| **تكلفة الاكتشاف المتأخر** | إصلاح خطأ يُكتشف بعد 6 أشهر يكلف 10× أكثر من إصلاحه الآن |
| **أولوية المستخدم** | أحمد (الشخصية المستهدفة) يحتاج لغة مستقرة للتعلم، وليس ميزات إضافية |
| **نضج المشروع** | المشروع فيه 105,000+ سطر كود — وقت التثبيت، وليس التوسع |

### 3.2 ما الذي لا يُجمّد؟

| مسموح | ممنوع |
|-------|-------|
| إصلاح أخطاء في ميزات موجودة | إضافة كلمات مفتاحية جديدة |
| إضافة اختبارات جديدة | إضافة عقد AST جديدة |
| تحسين رسائل الخطأ | إضافة أنواع بيانات جديدة |
| تحسين الأداء (بدون تغيير سلوك) | إضافة عوامل (operators) جديدة |
| توثيق وأمثلة تعليمية | توسيع SIR opcodes |
| إعادة هيكلة داخلية (refactoring) | إضافة ميزات تزامن جديدة |

### 3.3 تحليل المخاطر بدون التجميد

> **السؤال الحرج (John):** "إذا لم يستخدم أحد لغة ص بعد 6 أشهر، ما السبب الأرجح؟"

الإجابة: **"ميزات كثيرة معطلة"** — هذا هو السبب الأعلى احتمالاً. التجميد يعالج هذا السبب مباشرة.

## 4. البدائل المرفوضة

### 4.1 "إضافة ميزات مع اختبارات موازية"
**رُفض لأن:** تجربة المشروع أثبتت أن إضافة ميزات وتأجيل الاختبارات يؤدي لتراكم الفجوة. الاختبارات لا تُكتب "لاحقاً" عملياً.

### 4.2 "تجميد المترجم فقط والعمل على المفسر"
**رُفض لأن:** هذا يزيد الفجوة بين النظامين. كل ميزة تُضاف للمفسر بدون المترجم تزيد مدة اللحاق لاحقاً.

### 4.3 "لا تجميد — نثق بقدرة الفريق"
**رُفض لأن:** البيانات تقول العكس — 19 اختبار dual من مئات المسارات = تغطية < 10%.

## 5. العواقب

### إيجابية:
- ✅ تركيز كامل على الجودة والاستقرار
- ✅ كل أسبوع يضاف فيه 5+ اختبارات dual
- ✅ بعد 8 أسابيع: 65+ اختبار dual = شبكة أمان حقيقية
- ✅ رسائل خطأ متطابقة بين المفسر والمترجم

### سلبية:
- ⚠️ لا ميزات جديدة لمدة 8-12 أسبوعاً
- ⚠️ قد يبدو المشروع "جامداً" من الخارج
- ⚠️ مساهمون جدد قد يشعرون بالإحباط

### التخفيف من السلبيات:
- نشر تحديثات أسبوعية عن تقدم الاختبارات والاستقرار
- توجيه المساهمين لكتابة أمثلة تعليمية ووثائق بدلاً من ميزات
- التجميد مؤقت — ينتهي بتحقيق بوابة MVP

## 6. شروط رفع التجميد

| الشرط | المقياس | البوابة |
|-------|---------|---------|
| اختبارات dual كافية | ≥ 50 اختبار dual ناجح | Gate 0 |
| تغطية الميزات | ≥ 80% من فئات الميزات مُختبرة | Gate 0 |
| اختبارات سلبية | ≥ 10 اختبارات أخطاء | Gate 0 |
| CI مستقر | 0 اختبارات فاشلة على 3 منصات | مستمر |
| رسائل خطأ | متطابقة بين المفسر والمترجم | Gate 0 |
