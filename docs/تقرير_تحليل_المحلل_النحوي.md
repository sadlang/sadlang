## 🔴 المشكلة 1: كود ميت بنسبة 55% (الخطورة: حرجة)

### الوصف
مجلد `specs/` يحتوي على **22 ملف بـ 16,941 سطر** كود لا يُبنى أبداً. هذه الملفات:

1. **غير مُدرجة في أي CMakeLists.txt** في المشروع (فحص شامل)
2. **تُعرّف أنظمة أنواع خاصة بها** بدلاً من استخدام AST الموجود في المشروع
3. **تتضمن headers غير موجودة** في المشروع
4. **تستخدم namespaces مختلفة** عن النظام الأصلي

### أمثلة صادمة:

#### `specs/oop/parser_class.cpp` يعرّف:
- `enum class ASTNodeType` بالكامل (بينما المشروع يستخدم `shared/ast/include/ast_node.h`)
- `struct ASTNode` خاص به (بينما المشروع يستخدم `AST::ASTNode`)
- `enum class TokenType` كامل (بينما المشروع يستخدم `Lexer::TokenType` في `token.h`)
- `struct Token` خاص به (بينما المشروع يستخدم `Lexer::Token`)

#### `specs/oop/parser_constructor.cpp` يعرّف:
- `enum class ConstructorType` خاص به
- `struct ConstructorParameter` خاص به (بينما المشروع يستخدم `AST::Parameter`)
- `struct FieldInitializer` خاص به (بينما المشروع يستخدم `AST::FieldInitializer`)

#### `specs/async/parser_async.cpp`:
- يتضمن `#include "async_parser.hpp"` — **ملف غير موجود**
- يتضمن `#include "../include/parser.hpp"` — **ملف غير موجود**
- يتضمن `#include "../../ast/include/ast.hpp"` — **ملف غير موجود**
- يستخدم `namespace sad::parser` — **بينما المشروع يستخدم `Sad::Parser`**

#### `specs/contracts/parser_contracts.cpp`:
- يُعرّف أنواعاً **بالعربية**: `enum class نوع_العقد`, `enum class عامل_المقارنة`, `enum class محدد_كمي`
- هذه الأنواع لا علاقة لها بنظام AST في المشروع
- الكود مكتوب كنموذج أولي مستقل تماماً

### التأثير
- **صعوبة الصيانة**: أي مطوّر جديد سيقضي وقتاً في قراءة كود ميت
- **ارتباك**: تعريفات متعددة لنفس المفاهيم (Token, ASTNode, etc.)
- **حجم المستودع**: 17 ألف سطر كود بدون فائدة

## 🟡 المشكلة 3: تكرار الكلمة المفتاحية "حالة" في parseDeclaration (الخطورة: منخفضة)

في `parser_main.cpp`، الكلمة "حالة" (switch/case) يُتحقق منها **مرتين**:

```cpp
// المرة الأولى — سطر ~902:
if (check(TT::IDENTIFIER) && current_.getValue() == "حالة") {
    advance();
    return parseSwitchStmt();
}

// المرة الثانية — سطر ~966:
if (match(TT::KEYWORD_TEST) ||
    (check(TT::IDENTIFIER) && current_.getValue() == "اختبر" && (advance(), true)))
{
    // ... (ليس حالة لكن نفس النمط)
}
```

وكذلك `parseImportStmt()` و `parseExportStmt()` يُتحقق منهما **مرتين** في نفس الدالة:
```cpp
// المرة الأولى في بداية parseDeclaration():
if (match(TT::KEYWORD_IMPORT)) { return parseImportStmt(); }

// المرة الثانية في نهاية parseDeclaration():
if (match(TT::KEYWORD_IMPORT)) { return parseImportStmt(); }  // لن يصل أبداً!
```

## 🟡 المشكلة 4: تكرار إنشاء FunctionDecl (الخطورة: منخفضة)

في `parseFunctionDecl()` (ملف `parser_declarations.cpp`)، يوجد كتلتان شبه متطابقتان لإنشاء `FunctionDecl`:

```cpp
// كتلة 1 — مع decorators:
if (!decorators.empty()) {
    auto funcDecl = std::make_unique<FunctionDecl>(name.getValue(), ...);
    funcDecl->isMainFunction = isMain;
    funcDecl->lifetimeParams = std::move(lifetimeParams);
    funcDecl->preconditions = std::move(preconditions);
    funcDecl->postconditions = std::move(postconditions);
    funcDecl->whereConstraints = std::move(whereConstraints);
    funcDecl->docComment = std::move(docComment);
    return funcDecl;
}

// كتلة 2 — بدون decorators (نفس الكود!!):
auto funcDecl = std::make_unique<FunctionDecl>(name.getValue(), ...);
funcDecl->isMainFunction = isMain;
funcDecl->lifetimeParams = std::move(lifetimeParams);
funcDecl->preconditions = std::move(preconditions);
funcDecl->postconditions = std::move(postconditions);
funcDecl->whereConstraints = std::move(whereConstraints);
funcDecl->docComment = std::move(docComment);
return funcDecl;
```

**الحل**: دمج الكتلتين باستخدام `ExprList decorators = {}` في الـ constructor.

## 🟡 المشكلة 5: إفراط في إخراج std::cerr (الخطورة: متوسطة)

الكود النشط يحتوي على كتل ضخمة من `std::cerr` لطباعة رسائل خطأ مزخرفة بالإيموجي:

```cpp
std::cerr << "\n";
std::cerr << "❌❌❌ ========================================\n";
std::cerr << "  🚨 (AR) اكتشاف حلقة لا نهائية!\n";
std::cerr << "  🚨 (EN) Infinite Loop Detected!\n";
std::cerr << "========================================\n";
std::cerr << "📍 (AR) عالق في السطر " << ...;
std::cerr << "📍 (EN) Stuck at line " << ...;
std::cerr << "🔎 (AR) الرمز: '" << ...;
```

هذا النمط يتكرر **عشرات المرات** في `parser_main.cpp` و `parser_declarations.cpp`. المشاكل:
1. **أداء**: كل `std::cerr <<` هو عملية I/O مستقلة
2. **صيانة**: تغيير تنسيق الرسائل يتطلب تعديل عشرات المواقع
3. **معايير**: المشروع لديه `ErrorManager` و `errorBilingual()` لكنها لا تُستخدم في كل مكان

## 🟢 النقاط الإيجابية

### 1. تقسيم ممتاز للملفات النشطة
الكود النشط مُقسّم بشكل واضح ومنطقي:
- `core/` — البنية الأساسية (helpers, expressions, main loop)
- `declarations/` — التصريحات (functions, classes, modules)
- `statements/` — الجمل (if, while, for, try-catch)
- `ui/` — واجهة المستخدم التصريحية

### 2. اتباع أسلوب Recursive Descent Parsing
النظام يتبع هذا الأسلوب بشكل صحيح مع تسلسل أولويات العوامل:
```
parseExpression() → parseAssignment() → parsePipeline() → parseTernary()
→ parseNullCoalesce() → parseLogicalOr() → parseLogicalAnd()
→ parseBitwiseOr() → parseBitwiseXor() → parseBitwiseAnd()
→ parseEquality() → parseComparison() → parseTerm() → parseRange()
→ parseFactor() → parseUnary() → parsePower() → parsePostfix() → parsePrimary()
```

### 3. دعم ثنائي اللغة متسق
جميع رسائل الخطأ ثنائية اللغة (عربي/إنجليزي) بشكل متسق.

### 4. نظام التعافي من الأخطاء
`ErrorRecoverySystem` مدمج في `ParserCore` ويعمل جيداً مع كشف الحلقات اللانهائية.

### 5. دعم معالجة الكلمات السياقية
نمط التحقق المزدوج للكلمات السياقية مُطبّق بشكل صحيح:
```cpp
if (match(TT::KEYWORD_TRAIT) ||
    (check(TT::IDENTIFIER) && current_.getValue() == "سمة" 
     && peekNext().getType() == TT::IDENTIFIER && (advance(), true)))
```
