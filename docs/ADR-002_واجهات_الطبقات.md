## 1. السياق والمشكلة

لغة ص مبنية على 5 طبقات رئيسية متسلسلة:

```
Lexer → Parser → AST → Interpreter (شجري)
                    └→ SIR → LLVM CodeGen → ملف تنفيذي
```

**المشكلة الحالية:** الاعتماديات بين المكونات ضمنية ومباشرة:
- `InterpreterCore` يستورد `ast_node.h`, `statements.h`, `expressions.h`, `value.h` مباشرة
- `SIRBuilder` يستورد 10+ ملفات AST مباشرة (`expressions.h`, `statements.h`, `declarations.h`, `class_nodes.h`, `module_nodes.h`, `pattern_nodes.h`, `advanced_expr_nodes.h`, `property_nodes.h`)
- لا يوجد عزل بين الطبقات — تغيير في AST يؤثر على المفسر والمترجم معاً

**لماذا هذا مهم الآن؟** الخطة الشاملة 2026 تتضمن إعادة هيكلة (Strangler Fig) في المراحل 3-4. بدون واجهات مُعرّفة مسبقاً، الـ Strangler Fig سيتحول إلى فوضى.

## 2. القرار

نعتمد **Thin Facade Classes** كنمط تقني لعزل الطبقات، مع **قاعدة صارمة** تحكم الاستيراد.

### 2.1 النمط التقني: Thin Facades

**Thin Facade** = صنف abstract بسيط يعرّف الواجهة المطلوبة بين مكونين، بدون منطق أعمال.

**لماذا Facades وليس Abstract Interfaces كاملة؟**

| المعيار | Abstract Interfaces | Thin Facades |
|---------|-------------------|--------------|
| كلفة التنفيذ | عالية (إعادة هيكلة شاملة) | منخفضة (wrappers رفيعة) |
| التأثير على الكود الحالي | كبير (كل ملف يتأثر) | صغير (يُضاف فقط عند الحاجة) |
| العزل | كامل | كافٍ للمرحلة الحالية |
| التوافق مع Strangler Fig | مطلوب refactoring أولاً | يعمل كخطوة أولى تمهيدية |

### 2.2 قاعدة الاستيراد

> **القاعدة:** لا يستورد أي مكون ملفات header من مكون غير مجاور في السلسلة.

#### مصفوفة الاستيراد المسموح:

| المكون | يستورد من | يُمنع من |
|--------|----------|----------|
| **Lexer** | (لا شيء — مستقل) | Parser, AST, Interpreter, SIR, LLVM |
| **Parser** | Lexer (`token.h`, `token_type.h`) | Interpreter, SIR, LLVM |
| **AST** | (تعريفات مستقلة) | Lexer, Parser, Interpreter, SIR, LLVM |
| **Interpreter** | AST, Types (`value.h`) | Lexer, Parser, SIR, LLVM |
| **SIR Builder** | AST, SIR types | Lexer, Parser, Interpreter, LLVM |
| **LLVM CodeGen** | SIR types | Lexer, Parser, AST, Interpreter |

#### الاستثناءات المسموحة:
- `Position` (من Lexer) — يُستخدم في كل الطبقات لتتبع المواقع
- `Value` (من Types) — يُستخدم في Interpreter و VM
- `ModuleResolver` (من Modules) — يُستخدم في Parser و Interpreter و SIR Builder

## 3. الواجهات المُقترحة

### 3.1 واجهة تنفيذ الجمل — IStatementExecutor

```cpp
// facades/IStatementExecutor.h
// (AR) واجهة رفيعة لتنفيذ جمل AST — تعزل المفسر عن تفاصيل AST الداخلية
// (EN) Thin facade for AST statement execution — isolates interpreter from AST internals
#pragma once
#include "value.h"
#include <memory>
#include <vector>

namespace Sad::AST { class ASTNode; }

namespace Sad::Facades {

class IStatementExecutor {
public:
    virtual ~IStatementExecutor() = default;

    /// (AR) تنفيذ عقدة AST واحدة وإرجاع القيمة الناتجة
    /// (EN) Execute a single AST node and return the result value
    virtual Sad::Data::Value execute(const Sad::AST::ASTNode& node) = 0;

    /// (AR) تنفيذ كتلة جمل متعددة بالتتابع
    /// (EN) Execute a block of statements sequentially
    virtual void executeBlock(const std::vector<std::shared_ptr<Sad::AST::ASTNode>>& stmts) = 0;
};

} // namespace Sad::Facades
```

### 3.2 واجهة تقييم التعبيرات — IExpressionEvaluator

```cpp
// facades/IExpressionEvaluator.h
// (AR) واجهة رفيعة لتقييم تعبيرات AST
// (EN) Thin facade for AST expression evaluation
#pragma once
#include "value.h"
#include <memory>

namespace Sad::AST { class ASTNode; }

namespace Sad::Facades {

class IExpressionEvaluator {
public:
    virtual ~IExpressionEvaluator() = default;

    /// (AR) تقييم تعبير AST وإرجاع القيمة
    /// (EN) Evaluate an AST expression and return the value
    virtual Sad::Data::Value evaluate(const Sad::AST::ASTNode& expr) = 0;
};

} // namespace Sad::Facades
```

### 3.3 واجهة إدارة المتغيرات — IVariableManager

```cpp
// facades/IVariableManager.h
// (AR) واجهة رفيعة لإدارة المتغيرات — تعزل المتغيرات عن تفاصيل النطاقات
// (EN) Thin facade for variable management — isolates variables from scope details
#pragma once
#include "value.h"
#include <string>

namespace Sad::Facades {

class IVariableManager {
public:
    virtual ~IVariableManager() = default;

    /// (AR) الحصول على قيمة متغير بالاسم
    virtual Sad::Data::Value getVariable(const std::string& name) const = 0;

    /// (AR) تعيين قيمة متغير
    virtual void setVariable(const std::string& name, const Sad::Data::Value& value) = 0;

    /// (AR) التحقق من وجود متغير في النطاق الحالي
    virtual bool hasVariable(const std::string& name) const = 0;
};

} // namespace Sad::Facades
```

### 3.4 واجهة بناء SIR — ISIREmitter

```cpp
// facades/ISIREmitter.h
// (AR) واجهة رفيعة لإصدار تعليمات SIR من عقد AST
// (EN) Thin facade for emitting SIR instructions from AST nodes
#pragma once
#include <memory>
#include <string>

namespace Sad::AST { class ASTNode; }
namespace Sad::Compiler::SIR { class SIRModule; }

namespace Sad::Facades {

class ISIREmitter {
public:
    virtual ~ISIREmitter() = default;

    /// (AR) ترجمة عقدة AST إلى تعليمات SIR
    /// (EN) Translate an AST node into SIR instructions
    virtual void emit(const Sad::AST::ASTNode& node) = 0;

    /// (AR) الحصول على وحدة SIR الناتجة
    /// (EN) Get the resulting SIR module
    virtual std::shared_ptr<Sad::Compiler::SIR::SIRModule> getModule() = 0;
};

} // namespace Sad::Facades
```

### 3.5 واجهة توليد الكود — ICodeGenerator

```cpp
// facades/ICodeGenerator.h
// (AR) واجهة رفيعة لتوليد كود LLVM من SIR
// (EN) Thin facade for generating LLVM code from SIR
#pragma once
#include <string>
#include <memory>

namespace Sad::Compiler::SIR { class SIRModule; }

namespace Sad::Facades {

class ICodeGenerator {
public:
    virtual ~ICodeGenerator() = default;

    /// (AR) توليد كود من وحدة SIR
    /// (EN) Generate code from a SIR module
    virtual bool generate(const Sad::Compiler::SIR::SIRModule& module) = 0;

    /// (AR) إخراج الملف التنفيذي أو ملف الكائن
    /// (EN) Output the executable or object file
    virtual bool outputToFile(const std::string& path) = 0;
};

} // namespace Sad::Facades
```

## 5. خطة التنفيذ (Strangler Fig)

### 5.1 المبدأ
لا ننفذ الواجهات كلها دفعة واحدة. نتبع نمط **Strangler Fig**:

1. **أنشئ الواجهة** (facade header) — ملف صغير مستقل
2. **أضف wrapper** — الصنف الحالي ينفذ الواجهة (يرث منها)
3. **غيّر المُستخدمين** — واحداً تلو الآخر، ليستخدموا الواجهة بدل الصنف المباشر
4. **تحقق** — الاختبارات تمر بدون تراجع بعد كل تغيير

### 5.2 ترتيب التنفيذ

| الأولوية | الواجهة | متى | المبرر |
|---------|---------|-----|--------|
| P0 | `IStatementExecutor` | المرحلة 3 | الأكثر استخداماً في المفسر |
| P0 | `IExpressionEvaluator` | المرحلة 3 | يُكمّل IStatementExecutor |
| P1 | `ISIREmitter` | المرحلة 3-4 | نقطة الاتصال بين AST والمترجم |
| P1 | `ICodeGenerator` | المرحلة 4 | نقطة الاتصال بين SIR وLLVM |
| P2 | `IVariableManager` | المرحلة 4-5 | تحسين بنيوي |

### 5.3 شروط القبول

كل واجهة تُعتبر مكتملة عندما:
- [ ] ملف header الواجهة موجود في `facades/`
- [ ] الصنف الحالي يرث من الواجهة (ولو بدون تغيير مُستخدمين)
- [ ] اختبار وحدة واحد على الأقل يتعامل مع الواجهة
- [ ] لا تراجع في الاختبارات الموجودة

## 6. البدائل المرفوضة

### 6.1 "Modules TS / C++20 Modules"
**رُفض** لأن المشروع يستخدم C++17 والانتقال لـ C++20 modules تغيير كبير غير مبرر حالياً.

### 6.2 "Pimpl (Pointer to Implementation) لكل صنف"
**رُفض** لأن Pimpl يضيف overhead ذاكرة (heap allocation) لكل كائن، وليس ضرورياً لهدف العزل الحالي.

### 6.3 "لا واجهات — نعتمد على الاختبارات فقط"
**رُفض** لأن الاختبارات تكشف المشكلة بعد حدوثها. الواجهات تمنعها مسبقاً (compile-time vs runtime).

## 7. العواقب

### إيجابية:
- ✅ كل طبقة يمكن تطويرها واختبارها بشكل مستقل
- ✅ Strangler Fig يصبح آمناً — الواجهة تضمن عدم كسر المُستخدمين
- ✅ المساهمون الجدد يفهمون حدود كل مكون بوضوح
- ✅ تكلفة منخفضة — facades رفيعة بدون refactoring شامل

### سلبية:
- ⚠️ ملفات header إضافية (5-7 ملفات)
- ⚠️ Virtual dispatch overhead (ضئيل — ليس في hot path)
- ⚠️ يتطلب انضباطاً في كل PR جديد
